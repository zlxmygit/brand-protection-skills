# 品牌维权与仿冒处置

把用户填写的品牌、市场和资料转为可核验、可提交、可追踪的案件。跟随用户语言沟通；向机构提交的材料按其要求使用英文或当地语言。品牌、行业、官方域名、目标市场和材料位置均为案件输入，没有预设品牌或默认国家。

## 选择工作范围

按用户请求进行资料整理、线索核查、取证、渠道选择、材料起草、已授权的提交、补证/申诉或结果复核。先复用当前请求和指定的既有案件；新案件按 [资料接入](references/intake.md) 建立输入记录。用户可以自然语言提供资料，也可以填写 [品牌与市场表单](assets/intake-form.md)，不要求已经提供的信息重新填表。

复制 [案件结构](assets/case-record.json) 到用户指定或当前任务的独立私有目录，不改写空白模板。通用 Skill/共享仓库只保存规则、空白表单和通用模板；填写后的品牌信息、证书、联系人、目标域名和案件证据保存在仓库外。每个案件绑定品牌、资料来源、目标市场和操作范围；多品牌分别建档，不跨品牌复用权利或提交权限。

资料未齐时继续可完成的整理、公开取证、服务商识别和条件式草稿；仅暂停依赖缺失证据的法律主张或提交。先读取用户已提供的文件，能提取的字段不重复询问。市场未知则保留未知；“欧洲”等宽泛范围先记录原文，只有具体路径依赖时才确认国家。现有地区参考提供部分法域入口，不代表用户选择或全球覆盖；其他市场查对应官方程序，不套用已有国家规则。

## 核心判断

- 分开记录用户指称、页面观察、权利文件、实物鉴定、服务商决定和司法结论。每个结论绑定证据及时间，明确未知和相反证据。
- 分开判断复制作品、混淆/冒充官方、商标侵权、假冒商品、欺诈/钓鱼和产品安全。低价、未授权销售、共享主题、相似域名不能单独证明售假或诈骗；真实商品转售、评测、比较广告、合理使用及权利用尽需要核查。
- DMCA 针对受版权保护的具体作品；品牌词、产品参数或“卖假货”本身不是版权主张。摄影师/供应商授权、素材库和共享建站主题会影响可主张权利。
- 按文件正文区分商标、版权、专利、外观设计、技术图纸和授权材料；文件夹叫“专利”不决定文件类型。证书记载、实时登记状态、用户代理权限和具体侵权结论分别核验，不能互相替代。
- 域名注册商、注册局、DNS、CDN、源站主机、建站平台、支付商分别确认。一个 Cloudflare IP、Shopify 风格 URL 或支付 Logo 只能作为线索；共享 IP、证书、模板也不足以证明同一经营者。
- 选择能实现用户目标且证据充分的渠道。商标/假货/版权可并行，但每条主张分别举证，不把一份 DMCA 群发所有机构。

## 工作流程

1. **界定权利和目标。** 确认权利主体/代理权限、官方域名、授权渠道、重点市场，以及希望删除页面、停止收款、移转域名还是阻断货物流通。按 [取证与归属](references/evidence.md) 建权利矩阵，缺失字段写明待补，不猜测注册号、所有权、金额或宣誓事实。
2. **先保存，再投诉。** 采集具体商品和内容 URL、跳转链、完整上下文、官方对照和适用的公开技术信息。网页文本检索不是浏览器截图；工具失败不是网站已停用。保存原件、采集时间/时区、方法、哈希与证据索引，遵循证据参考中的限制。
3. **建立渠道计划。** 针对每个域名/页面记录接收方角色、归属证据、官方入口、权利依据、材料缺口、期望措施和其能力边界。按需要读 [线上渠道](references/online-channels.md) 与 [域名、地区和海关](references/legal-regions.md)；专利/外观设计使用 [专项分流](references/patents-designs.md)。优先处理持续交易、明显混淆、已发生损害及有证据的安全风险；不要编造风险评分或损失。
4. **形成可审阅材料。** 使用 [投诉与升级模板](assets/complaint-templates.md)，每个接收方独立生成。逐项链接“原作品/商标—被诉 URL—证据—请求”。正式表单和最新规则优先于模板；未知字段留在草稿，未核实的法条、假货结论或签名不能进入可提交版本。
5. **按实际授权提交。** 建立 Skill、调查或起草本身不授权外发。用户若已明确授权相应收件方/案件/材料和行为，不重复索取同一批准；仍须核实声明、签名权限、费用及披露内容。需要补充授权时，先给出具体收件方、最终文本、附件、所需声明与费用。不得自行签署宣誓、冒充律师、接受和解/管辖条款、付款测试购买、提起诉讼或公开发布指控。缺少这些权限不妨碍完成独立准备工作。
6. **持续跟踪与验收。** 提交后立即按 [持续跟进规则](references/follow-up.md) 建立回执、反馈来源、应答期限和下一次行动。用户要求持续跟进时，把已授权的检查、原工单催办、补证和升级推进到明确结果；无响应不能默认为结案。逐项记录“已提交”“已受理”“决定采取措施”“实际复核”。收到反通知、扣货通知或域名裁决后，优先处理其真实期限。发现已发送投诉存在错误时，按跟进规则冻结相关主张并逐渠道准备更正/撤回，保留独立补救事项。新的投诉、签名、费用与诉讼不得超出既有授权。

## 按目标验收

| 目标 | 可接受的完成证据 | 不足的证据 |
|---|---|---|
| 下架内容/商品 | 原始 URL 与变体复查、时间/地区/状态，结合机构结果 | 单次超时、403、搜索未命中 |
| 搜索/广告移除 | 对应产品/广告 ID、查询/地区及复核结果 | 源站还在与否，或泛称“全网消失” |
| 限制支付 | 服务商可披露的处理结果与有限公开复核；说明不可见部分 | 支付 Logo 消失、擅自下单测试 |
| 域名移转 | 裁决与实际注册商账户/域名控制权确认 | 仅胜诉邮件、DNS 暂停 |
| 海关措施 | 备案批准和具体扣留/处理分别记录 | 申请提交即称查扣成功 |

## 持续推进

用户要求持续跟进时，读取 [持续跟进规则](references/follow-up.md)，填写案件的 `follow_up`、`followup_tasks` 和 `outbound_attempts`。记录版本、字段和队列输出按 [案件格式与迁移](references/case-format.md) 核对。每个未结目标/渠道都应有下一步、时间和阻塞原因；一条渠道无回应时继续其他有证据且获授权的路径。用户尚未选择持续跟进的其他案件不自动启用。

定时检查依靠实际调度器、可读的反馈源和案件记录运行，Skill 文件本身不会后台唤醒。按规则验证并登记调度状态；未创建、离线、权限失效或执行失败必须如实报告。可用 [只读到期队列](scripts/followup_queue.py) 筛选本轮待办，但脚本不发信、不重提投诉，也不代替发送前的最新反馈核验。

对超时先核实送达和反馈，再同工单催办/补证；在渠道允许且有明确理由时重提或升级。不能通过重复投诉、换身份或改标签绕过实体驳回。确认移除后按计划复查；镜像/新域名仍须建立新证据，不自动继承旧站结论。

交付时给出当前结论、逐目标状态、已完成材料、未验证边界和下一项必要行动。沿用案件内同一份“要求—核验案例—材料—证据—状态”清单；不得把草稿完成写成投诉成功。
