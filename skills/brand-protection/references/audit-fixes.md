# v1.8.1 审计修复与兼容说明

本版修复 v1.8.0 审计发现的六类缺口，并调整更正关系校验的工作量。没有新增发送器、调度器或默认外发权限。案件格式仍为 `schema_version: 1.3`，工具不自动改写私有记录。

## 审批材料依赖

提交前审查使用 `snapshot_version: 1.1`。正文、附件和主张证据之外，还检查本次权利引用的 `material_ids`、主体的 `authorization_evidence_ids`、指称的正反证、观察证据、目标关系证据和服务商归属证据。派生副本的父记录也在检查范围内。

证据文件沿用 `original_path`，材料文件沿用 `source_path`。两类记录均须有实际文件和匹配的 SHA-256。只登记远端地址或响应哈希、没有保全本地原文的记录，不能作为已完成的文件依赖。工具不会为通过检查而自动下载、猜测或补写材料。

`authorization_material_ids` 可用于记录行动或主体的授权文件。结构化的 `authority_verification`、`registry_verification` 和跟进授权可用 `evidence_ids`、`material_ids` 引用本案记录。支持的引用名由校验器明确列出；自由文本中的路径不作为已核对的文件引用。

缺失、重复、循环、越界或明确冲突的引用会阻止审查。依赖不完整时，快照返回 `complete: false` 和 `sha256: null`；即使手工填写全部审批检查项，也不能得到匹配状态。有效快照包含材料记录及实际文件哈希。每次最多核对 1,000 个依赖，累计文件字节不超过 50 MiB；单文件继续使用 10 MiB 上限。

旧版快照没有覆盖这些依赖，因此升级后必须重新核对实际材料，再记录新审批。不要自动替换旧审批的哈希来绕过复核。审批记录的 `version: 1.0` 不变，实际匹配依据由快照版本区分。

## 本次主张的范围

行动可填写非空 `right_ids`，明确本次使用的权利。`authority_party_ids` 指定额外的签署或代理主体，权利人始终保留。未填写这两个字段的旧案，继续保守纳入全部权利和主体。

指称、观察记录有明确目标且与本次行动无关时，不纳入本次快照。没有目标字段的旧记录按案件级上下文处理，不能据此丢弃可能影响主张的相反证据。未被引用的材料文件不会被读取。

这些字段只缩小技术检查范围，不证明主张成立。主体核验、真实授权和最新反馈仍按原规则处理。

## 品牌、案件与目标关联

调查、导出、渠道检查和审批依赖共用记录关联检查。记录明确填写了 `brand_id`、`case_id` 或目标范围时，必须与当前案件及用途一致。显式空值、坏类型和相互冲突的目标字段不能当作省略。

旧证据省略品牌标签时，仍允许按原有案件关联处理，但这不证明品牌归属。共享材料或关联品牌不提供自动豁免；有明确冲突时先核实关系和实际授权，不要仅改标签使检查通过。派生副本不能通过自己的标签掩盖父记录的冲突。

导出仍只复制逐项批准的字节，不自动上传原件。父链检查不会把父文件一起打包。

## 服务商与目标对应

单目标渠道记录必须填写 `providers[].target_id`。工具不再根据“案件只有一个目标”推定服务商归属。原有正向测试夹具补充了这一字段，业务断言没有放宽。

多目标行动使用 `target_attributions` 逐项记录归属：

```json
{
  "id": "provider-1",
  "organization": "Cloudflare",
  "role": "reverse_proxy",
  "target_ids": ["target-1", "target-2"],
  "verified_at": "2026-11-13T02:00:00Z",
  "attribution_evidence_ids": ["attribution-1", "attribution-2"],
  "target_attributions": [
    {"target_id": "target-1", "evidence_ids": ["attribution-1"], "verified_at": "2026-11-13T02:00:00Z"},
    {"target_id": "target-2", "evidence_ids": ["attribution-2"], "verified_at": "2026-11-13T02:00:00Z"}
  ]
}
```

示例只说明字段。每项证据必须来自本案，明确目标时也须对应本项。每个行动目标都要有归属记录。晚于渠道审查的核验要求重新审查。单独列出两个域名，不能代替各自的归属证据。

## 首次通知与后续任务

`initial_notice` 现在是队列认可的外发类型。初次通知可以保留自己的任务、去重键和发送尝试，后续催办使用不同的任务及轮次。已经核清的首次发送不会再因类型不兼容阻断正常跟进。

`prepared`、`in_flight`、`outcome_unknown` 和进行中的首次任务仍形成外发阻断。已成功发送的相同去重键不能重用。不要删除历史任务或将初次通知改写成重提。

## 私有目录与网络输入

私有目录检查覆盖 Git 克隆、带项目布局和发布清单的源码 ZIP，以及独立 Skill 安装目录。宿主的 `.agents/skills`、`.codex/skills` 和 `.claude/skills` 扫描目录也不接收私有输出。普通目录仅有 README 不会被误判成项目根。符号链接和父目录穿越仍拒绝；Windows 访问控制仍需由运行者配置。

RDAP 检查声明长度与实际字节数，拒绝重复或歧义长度、长度与传输编码冲突、超限、压缩及不完整分块。失败时返回来源失败和未知注册状态，不保留成功证据，也不自动重试。处理依据为 [RFC 9112 第 6.3、8 节](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)。没有长度头的连接关闭定界仍按 HTTP 客户端规则读取；这不构成全流程超时保证。

## 复测与剩余边界

原有 245 项测试继续执行。新增测试保留审计的 13 项断言，并覆盖文件依赖、关联冲突、首次发送历史、输出目录及 HTTP 分块错误。构建同时测试实际解压后的脚本。最终数量与执行结果见本版发布附件 `VALIDATION.json`。

更正关系改为一次遍历验证，避免为每条记录重复扫描祖先链；最多接受 10,000 个行动。长链和非关联环有专门测试。

这些测试不认证权利人或审批人身份，不证明真实发送、独占写回、后台监测或第三方受理已经验收。`authorizes_submission` 继续为 `false`。
